# 해설

1. 파티션 0은 커밋 0, 반영 0건입니다. 첫 레코드에서 계속 seek로 되돌아가므로 뒤의 9건도 처리되지 않습니다. 파티션 1은 같은 소비자가 읽는데도 커밋 10, 반영 10건입니다. 막힘은 소비자 전체가 아니라 실패한 레코드가 있는 파티션 단위로 생깁니다. 검증 실행에서는 2초 동안 16~17번 재시도했고, 조회를 고친 뒤 파티션 0도 따라잡았습니다.
2. zero 소비자는 v1 이벤트를 받아도 원본의 현재 상태(v2)를 조회하므로 "제목 v2"를 유지합니다(API 1회). fat 덮어쓰기는 "제목 v1"로 돌아갑니다. version 비교 소비자는 v1을 버리고 "제목 v2"를 유지합니다. zero payload는 DLT 재처리를 "다시 조회하라는 신호"로 만들기 때문에 재처리 시점이 늦어도 과거로 돌아가지 않습니다.
3. 검증 실행 네 번 모두 30건 중 13건이 DLT로 갔고 17건이 복구 후 처리됐습니다. 이 13건은 데이터에 문제가 없는 정상 이벤트입니다. 장애가 길수록 숫자는 커집니다. `/health`를 먼저 보는 정책은 원본 장애 동안 시도 횟수를 세지 않고 200ms씩 15번 멈췄다가, 복구 후 30건을 모두 처리했고 DLT는 0건이었습니다.
4. 검증 실행(한 배치에 200건이 모두 들어옴) 기준입니다. 이벤트마다: 200회, 약 4.8~5.4초(하한 200 × 20ms = 4초). 중복 제거: 50회, 약 1.2~1.3초. 여러 건 조회 API: 1회, 약 30ms. 8개 동시 조회: 200회, 약 0.6~0.7초. 동시 조회는 시간을 줄이지만 원본 호출 수는 그대로이고, 원본에 순간 동시 요청 8개를 만듭니다. 중복 제거 효과는 같은 글의 이벤트가 한 배치에 몰려 있을 때만 생깁니다.
5. 100건 배치는 처리에 약 3초가 걸려 2초 제한을 넘습니다. 커밋은 `CommitFailedException`으로 실패하고, 소비자는 그룹에 다시 들어가 커밋 0부터 같은 100건을 다시 받습니다. 검증 실행에서는 약 10~11초 동안 커밋 실패 3번, 조회 300번(같은 100건을 세 번), 최종 커밋 0이었습니다. 20건 배치는 약 0.6초씩이라 커밋 5번에 조회 100번으로 끝났습니다. 원본이 느려지는 것만으로 소비자가 같은 일을 반복하며 원본에 부하를 더하는 고리가 생깁니다.

## 바꿔 보기

- `MAX_POLL_INTERVAL_MS = "5000"`이면 100건 배치(약 3초)가 제한 안에 들어옵니다. 검증 실행: `SEEN ... maxPollRecords=100: fetches=100 commitsOk=1 commitsFailed=0(-) committed=100 in 3398ms`, 그리고 `FAIL 100-record batches never commit and re-fetch`(실습은 실패하는 쪽을 판정하므로)였습니다. 제한을 늘리면 문제는 사라지지만, 소비자가 정말 멈췄을 때 그룹이 알아차리는 시간도 함께 길어집니다.
