# 예상·실행·비교

실행 전에 각 질문의 답을 한 줄씩 적어 두고, 실행 결과의 `PASS`·`SEEN` 줄과 비교하세요.

1. 파티션 0의 첫 레코드(글 ID 1)만 조회가 계속 500입니다. 무한 재시도 소비자 하나가 파티션 0·1을 함께 읽습니다. 2초 뒤 파티션 0과 1의 커밋 오프셋은 각각 얼마일까요?
2. 글 30의 v1 이벤트가 DLT로 갔고, 원인을 고친 뒤 v2 이벤트가 정상 반영됐습니다. 이제 DLT의 v1을 재처리하면 zero 소비자, fat(덮어쓰기), fat(version 비교)의 제목은 각각 무엇일까요? zero 소비자는 API를 몇 번 부를까요?
3. 원본 전체가 3초 동안 503입니다. "같은 레코드가 3번 실패하면 DLT" 정책은 정상 이벤트 30건 중 대략 몇 건을 DLT로 보낼까요? 실패할 때 `/health`를 먼저 보는 정책은요?
4. 원본 응답이 요청마다 20ms 걸립니다. 이벤트 200건(글 50개 × 4번)을 다음 방식으로 처리하면 조회 횟수와 처리 시간은 대략 얼마일까요? 이벤트마다 순서대로 / 배치 안에서 글 ID 중복 제거 / 여러 건 조회 API 한 번 / 8개 동시 조회.
5. `max.poll.interval.ms`가 2초이고 조회가 30ms입니다. 한 번에 100건을 받아 모두 조회한 뒤 커밋하면 커밋은 성공할까요? 9초 동안 조회는 몇 번 일어날까요? 20건씩 받으면요?

## 바꿔 보기

- `SourceFailureLab.MAX_POLL_INTERVAL_MS`를 `"2000"`에서 `"5000"`으로 바꾸고 `./play-zero-payload-02 verify`를 실행하세요. 어느 판정이 실패할지, 그 직전 `SEEN pollInterval` 줄의 `fetches`·`committed`가 얼마일지 먼저 예상하세요. 확인한 뒤 되돌리세요.
