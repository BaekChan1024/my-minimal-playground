# 해설

1. Outbox: Saga 20개가 모두 끝납니다. GENERATING 상태와 `Generate` 명령이 한 트랜잭션으로 Outbox에 들어갔으므로, 다시 뜬 릴레이가 보내지 못한 행을 보냅니다. 커밋하고 바로 보내기: 1개가 GENERATING에서 영원히 멈춥니다. 상태는 커밋됐는데 `Generate`는 나가지 않았습니다. 재시작한 오케스트레이터는 오프셋을 커밋하지 못한 `PostLocked`를 다시 받지만, 이미 처리한 메시지 ID라서 Inbox가 버립니다(Inbox가 없었더라도 상태가 이미 GENERATING이라 상태 가드가 무시합니다). 그 Saga는 예약 500과 글 잠금 1개를 쥔 채 남습니다. 두 방식 모두, 크래시 직전 poll 묶음에서 이미 처리했던 메시지를 다시 받아 Inbox가 버렸고, 그 수는 실행마다 1~6건으로 달랐습니다. 이 실험은 시한을 끄고 실행했습니다(시한을 켰다면 멈춘 Saga는 보상되어 예약과 잠금이 풀렸을 것입니다. 실험하지 않았습니다).
2. 같은 글의 잠금을 먼저 Saga가 쥐고 있으므로 10개 모두 `BUSY`로 실패하고 예약을 돌려줍니다. 2초 시점에 잠긴 글 10개, 앞선 Saga 10개는 GENERATING입니다. AI가 돌아오면 앞선 10개는 끝납니다. 시한이 없으면 멈춘 Saga가 자원을 쥔 채 남의 요청을 계속 막습니다.
3. 맞지 않습니다. 0.5초 시한으로 20개 모두 보상되어 잠금이 풀렸지만(BUSY 0), 돌아온 AI는 밀린 `Generate` 20건을 모두 처리해 토큰 2,540을 썼고, 늦게 온 결과는 이미 끝난 Saga에 도착해 무시됩니다. 사용량 0 / 실제 2,540. 늦은 결과를 받으면 `ChargeLate`로 기록하게 하면 사용량 2,540 = 실제 2,540으로 맞습니다. 다만 두 경우 모두 20건의 생성은 결과를 쓰지 못한 비용입니다. AI에 취소를 알리는 장치가 있어야 줄일 수 있습니다.
4. 기다리기: 5개 모두 COMMITTING에 멈춥니다. Usage는 이미 확정했으므로 숫자는 맞지만 Saga는 끝나지 않습니다. 다시 보내기: 0.2초 뒤 같은 명령을 새 메시지 ID로 보내고(5건), Usage는 이미 확정된 예약이라 아무것도 바꾸지 않고 응답해 5개 모두 COMPLETED입니다. 새 메시지 ID라 Inbox는 중복으로 알아보지 못했고, 업무 규칙의 상태 조건이 막았습니다. 그 조건이 없으면 다시 보낸 확정이 또 반영되어 사용량이 1,300 / 실제 650으로 두 배가 됩니다. 보상: 요약 5개가 내려가고 Saga는 COMPENSATED지만, 확정된 예약은 해제되지 않아(이미 COMMITTED) 사용량 650은 그대로 남습니다. 비용은 냈는데 결과는 없는 상태입니다. 피벗 뒤에서는 보상이 아니라 끝까지 다시 시도해야 합니다.

## 바꿔 보기

- 시한이 3초면 AI가 2초에 돌아오므로 시한이 오기 전에 앞선 Saga가 진행됩니다. 2초 시점은 시한 없음과 같은 `{COMPENSATED=10, GENERATING=10}`이고, 판정이 `FAIL deadline releases {COMPENSATED=10, GENERATING=10}`에서 멈춥니다. 시한은 장애보다 짧아야 의미가 있고, 정상적으로 오래 걸리는 작업보다는 길어야 합니다.
