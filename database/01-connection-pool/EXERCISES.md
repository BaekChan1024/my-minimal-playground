# 실행 전 예상과 직접 확인

## 예상

1. 풀 크기 2에서 두 연결을 빌려 `SELECT 1`을 끝냈습니다. 반환하지 않았다면 세 번째 조회는 어디에서 기다릴까요? DB의 `idle`과 풀의 `idle`은 같은 뜻일까요?
2. SQL 뒤에 DB가 필요 없는 200ms 작업이 있습니다. 풀을 2에서 4로 늘리는 것과 반환을 앞당기는 것 중 각각 어떤 시간을 바꿀까요?
3. 첫 연결의 UPDATE가 미커밋 상태일 때 두 번째 UPDATE와 세 번째 SELECT는 각각 어디에서 기다릴까요?
4. `statement_timeout`을 줄이면 `getConnection()` 대기도 짧아질까요?

## 실행과 비교

`./play-database-01`을 실행하고 예상과 출력이 다른 부분을 기록하세요.

- `held-idle`의 풀 지표와 PostgreSQL 상태를 함께 읽어 보세요.
- `lock-cascade`에서 두 번째 작업과 세 번째 작업의 시간을 구분하세요.
- `batch` 세 줄에서 전체 시간·평균 획득 시간·평균 점유 시간을 비교하세요.
- timeout 세 종류의 SQL 진입 여부와 예외를 설명해 보세요.
