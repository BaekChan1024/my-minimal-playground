# 실행 후 해설

- DELETE를 커밋하면 새 조회의 행 수는 줄지만 heap 파일이 즉시 줄지는 않습니다. 실측에서는 20,000→2,000행, heap 11,706,368바이트 유지였습니다.
- 파일 내부의 정리와 운영체제로의 공간 반환은 다릅니다. 일반 VACUUM 후 내부 빈 공간을 확인하고 실제 재삽입으로 재사용을 확인합니다.
- 같은 크기의 18,000행 재삽입 뒤 heap은 유지됐지만 인덱스 크기는 늘었습니다. heap과 전체 저장 공간을 같은 값으로 취급하지 마세요.
- 열린 REPEATABLE READ 스냅샷은 여전히 옛 10,000행을 읽습니다. 새 조회에는 1,000행만 보였지만 VACUUM 후에도 이전 버전 9,000개가 남았습니다. reader 종료 후 재VACUUM에서 정리됐습니다.
- pgstattuple의 dead 분류와 즉시 제거 가능성은 다릅니다. 해당 함수는 HeapTupleSatisfiesDirty 기준으로 dead를 판단하며, 오래된 스냅샷을 위한 보존 여부와 동일한 조건이 아닙니다.
- FULL은 살아 있는 행을 보존하며 파일을 재작성했습니다. 공간이 줄었지만 공식 문서상 새 복사본의 공간과 ACCESS EXCLUSIVE 잠금 비용이 있습니다. 이 실습은 최대 디스크 사용량이나 동시 부하의 대기 시간을 측정하지 않았습니다.
- 트랜잭션 블록 안의 VACUUM은 SQLState 25001로 거절됐습니다. 실습의 정상 VACUUM 명령은 auto-commit 연결에서 실행합니다.

## 예상과 달랐던 결과

삭제 후 첫 측정에서 dead=7, free=10,500,264바이트가 관측됐습니다. 18,000개가 그대로 남아 있지 않았습니다.
그 측정에는 count(*)와 pgstattuple 접근이 포함됩니다. 명시적 VACUUM 없이도 페이지 접근 중 정리가 일어날 수 있으므로,
VACUUM만이 모든 빈 공간을 만들었다고 해석하지 않습니다. 각 조회의 개별 정리 기여를 분리 측정하지 않았습니다.

## 선택 문제의 예상 (별도 실행하지 않음)

payload를 키우면 동일한 페이지 수에 행을 담기 어려워져 heap 증가 가능성이 있습니다.
READ COMMITTED에서는 뒤 문장이 새로운 스냅샷을 사용할 수 있으므로 원본의 오래된 조회 보존 조건이 달라집니다.
파일 끝의 빈 페이지는 일반 VACUUM도 줄일 수 있지만 빈 페이지 위치와 잠금 확보 등의 조건이 맞아야 합니다.
선택 조건의 실제 결과는 직접 실행하고 확인해야 하며, 기본 실측 수치에 포함하지 않습니다.
