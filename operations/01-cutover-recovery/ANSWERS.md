# 관측 결과와 해설

1. 양쪽 모두 2행이지만 원본은 `[1, 2]`, 최신 상태는 `[1, 3]`입니다. 옛 상태를 선택하면 ID 1 수정이 사라지고 삭제한 2가 돌아오며 새 글 3은 없습니다. 단순 COUNT는 데이터 보존 검증이 아닙니다. 여기서는 옛 DB를 실제 재가동하지 않고 보존된 `legacy`와 `modern` 값을 비교합니다.
2. 최신 복사본을 옛 구조로 역변환하고 ID·제목·본문·파일 키·정렬한 태그의 정규화 결과를 비교합니다. `blocks` 형식은 옛 구조로 처리할 수 없다는 실습 가정에 따라 삽입 전 거부하며 대상은 0행입니다. 검증 뒤 값을 억지로 버리는 변환을 하지 않습니다. 운영의 실제 새 형식 지원 여부를 뜻하지 않습니다.
3. 명시적 ID INSERT는 새 테이블의 bigserial 시퀀스를 따라 올리지 않습니다. 실습에서는 첫 자동 ID 1이 기존 행과 충돌합니다. 비어 있지 않은 격리 대상에서 `setval(sequence, max(id), true)` 후 다음 쓰기는 4입니다. 시험 행을 지우고 다시 원래 복구 행과 비교합니다. 이 공식만으로 빈 테이블·다른 증가폭·동시 쓰기·외부 ID 발급기를 처리하지는 않습니다.
4. 최신 글은 cover-3, cover-4를 참조하지만 옛 파일 백업에는 없습니다. 최신 파일을 복사해도 하나를 손상시키면 SHA-256 불일치가 검출됩니다. 다시 복사하면 두 참조가 통과합니다. 해시 기대값은 쓰기가 없는 fixture에서 수집했으므로 DB와 오브젝트 저장소의 원자적 백업을 검증한 것이 아닙니다.

행 비교는 이 fixture의 필드만 다룹니다. 모든 실제 테이블·권한·외래 키·트리거·확장·애플리케이션 읽기 경로를 검증하지 않습니다. 사용자 숙지는 자동 PASS와 별개입니다.
